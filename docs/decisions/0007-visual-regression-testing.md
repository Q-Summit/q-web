# 0007 · Git-native visual regression testing

- **Status:** Accepted
- **Date:** 2026-07-29
- **Trigger:** The Webflow port locked in a component look that only humans eyeballing preview URLs protect; a shared token or `global.css` edit can silently reflow every page, and nothing catches it before merge.

## Context

The site is a token-driven design system: one change in `src/styles/tokens.css` or `global.css` cascades across dozens of components. Preview-URL review catches what a reviewer happens to open; it does not catch an unintended shift three pages away. Content is CMS-driven, so the real layout risk is content the site has never rendered before (a long speaker bio, an empty partner list, German compounds).

The constraints that decided every other vendor choice apply here too: EU data residency, `$0`, no US SaaS, no cookies or third-party runtime requests on the site itself ([ADR-0003](0003-posthog-cookieless-analytics.md), [`08-concepts.md`](../architecture/08-concepts.md)). The repo is public, so GitHub Actions minutes are free.

## Considered options

1. **Hosted SaaS (Chromatic, Percy, Argos)**: upload snapshots to a service that stores baselines and hosts the review UI. Pro: best-in-class review UX out of the box. Con: US data residency and a paid cliff (`$100` to `$179`/mo past the free tier), both ruled out by our own constraints.
2. **Storybook + a Storybook VRT tool**: the usual component-workshop path. Pro: mature ecosystem. Con: Storybook cannot render `.astro` components without an experimental community framework, and this app is pure Astro with no framework islands, so it would mean adopting a fragile pipeline for the exact thing we want to gate on.
3. **Git-native: Playwright screenshots a component gallery, baselines committed as PNGs**: render each component variant through the real Astro build, diff against committed images, in CI. Pro: `$0`, EU-resident (renders in our CI, images in our repo), no new runtime on the site, and it renders production Astro, not an approximation. Con: no hosted point-and-click "accept" button; accepting is a baseline regeneration plus merge.

## Decision

Option 3, in the **advisory review** shape proven by the Noa-IQ marketing-website VRT (not a hard blocking gate). A dev-only gallery (`src/pages/vrt/`, built only when `VRT=1`, absent from prod) renders every component variant declared in a co-located `*.vrt.ts` file. Playwright screenshots each variant at three breakpoint widths against the built static site and diffs it against committed baselines under `apps/web/tests/visual/__screenshots__/`, **inside the pinned Playwright image** so rendering matches how baselines are generated.

On a PR this runs as a dedicated **advisory** job (`visual.yml`, `continue-on-error`): a diff **never blocks the merge**. Instead it posts a sticky comment linking a click-to-view Cloudflare Pages report and, when a `VRT_PAT` is configured, auto-pushes the refreshed baselines onto the PR branch. Protection is the reviewer seeing the diff (in the comment and the PR's image-diff) before approving, the Chromatic/Percy model, rather than a red status. This deviates from the repo rule that gates live in `pnpm run check`: the visual check is deliberately advisory and needs `pull-requests: write` + Cloudflare, none of which belong in the blocking check.

What decided it: the failure being protected against is a cascade the author did not intend and a reviewer would not think to open. A full render-and-diff of every variant surfaces that, and committed baselines keep it EU-resident at `$0`. Advisory-plus-comment was chosen over a hard block for developer flow: a visual change is usually intentional, so the default should be "show me what changed", not "red until you run a command". On merge to main, `visual-propagate.yml` updates open PR branches so baselines stay cross-PR correct. Branch-protection "require up to date" is deliberately not required: committed PNG baselines get a git 3-way merge (same-component changes conflict and force a re-render), and `Checks` re-runs on `push: main`, so correctness holds without the per-PR update chore.

## Consequences

- `apps/web` gains `@playwright/test` (a dev dependency and free OSS tool, not a new vendor or runtime) and a `vrt` / `vrt:update` / `vrt:docker*` script set. The advisory pipeline is four workflows (`visual.yml`, `visual-propagate.yml`, `visual-cleanup.yml`, `update-visual-baselines.yml`) plus two helpers (`scripts/check/vrt-report.mjs`, `scripts/check/vrt-cleanup.mjs`). Runbook, modes, and one-time setup: [`../dev/visual-testing.md`](../dev/visual-testing.md).
- The check is advisory and browser-heavy, so it is NOT part of `pnpm run check` (local or CI); it runs only in `visual.yml` on PRs. A green local `check` does not include the pixel diff; use `pnpm --filter web run vrt:docker` to compare locally.
- Three modes degrade gracefully by secret presence: COMPARE (comment + artifact, no secrets), PUBLISH (hosted Cloudflare Pages report, `CLOUDFLARE_*`), AUTO (auto-commit baselines to the PR, `VRT_PAT`). Requires one-time infra (a `q-web-vrt-reports` Pages project, `VRT_PAT`, branch protection) recorded in [`../dev/go-live.md`](../dev/go-live.md).
- The PR is rendered on top of current `main` (an in-job `git merge`) and always diffed against `main`'s committed baselines, never the PNGs on the branch (matching how Chromatic/Percy/Argos/reg-suit resolve the "before" from the base branch, not a PR-authored file). This keeps a change visible even if the author pre-committed its baseline, prevents cross-PR clobber, and means a hand-edited/OS-mismatched PNG is never what we compare against. After the in-job merge the workflow inspects the actual conflicted paths itself (not an in-tree merge driver, which a PR could edit): a conflict only in the baseline dir is fine (baselines are reset to the base anyway), while any conflict outside it is a real code conflict, so the job skips with an "update your branch" comment rather than diff stale code. AUTO commits the re-derived baselines anchored to the PR head (no bot merge commit), and only the baselines it refreshed, so a PR's baseline deletion is not resurrected.
- Nothing reaches visitors: the gallery is `getStaticPaths`-gated on `VRT=1` and emits to a separate `dist-vrt/`, so a prod build never contains it. The cookieless/no-third-party property is untouched. The hosted report is a separate Cloudflare Pages project (`q-web-vrt-reports`); it is public, which is safe because every screenshot renders template fixtures with images neutralized to placeholder glyphs, so a report never carries production content. An Access policy is optional.
- Images are neutralized before every screenshot: each `<img>` (plain or `astro:assets`) is swapped for a grey image-placeholder glyph of the same intrinsic size, and the hero `<video>` is hidden. Real photos live only in the gitignored `public/media/`, so this keeps real content out of committed baselines and keeps them reproducible on a fresh checkout, while the element's CSS (`border-radius`, `object-fit`, box) is untouched so image-layout regressions still show.
- Coverage is a component's own `*.vrt.ts`; a component with none is simply not reviewed. Whether to enforce a coverage floor is left open. Removing a variant leaves orphan PNGs until AUTO / `vrt:update` / `--prune-only` deletes them (Playwright never removes baselines).
- Not covered: production-content regressions (an editor's live input), cross-browser rendering (Chrome only), dark theme (until one ships), and interactive/JS-toggled states (the gallery screenshots the static SSR render, so a disclosure like the mobile nav open menu is captured closed, not open). Because the check is advisory, an unintended regression is not hard-blocked; it relies on the reviewer reading the comment and the PR's image diff before approving.
